# قفل التسجيل + قائمة السماح — الخطوة 2 من خط الأدمن (T17 — 3A-892)

**المهاجرة:** `0057_registration_lock_allowlist.sql` (بعد 0055 إلزاماً —
تعتمد `is_platform_admin()`). **كود فقط — غير مطبّقة على الإنتاج**
(قاعدة تجميد الفيز: التطبيق عند تجميد فيز 2 + بوابة QA).

## ما الذي بُني؟

| القطعة | الوصف |
|---|---|
| `platform_settings` | مفاتيح المنصة كبيانات؛ البذرة الوحيدة `registration_open = true` — **صفر تغيير سلوكي حي**: التسجيل يبقى مفتوحاً كما هو اليوم حتى قرار صريح بقلبه. قراءة للأدمن فقط، ولا UPDATE للعميل إطلاقاً (service role / SQL حتى واجهة اللوحة في الخطوة 7). |
| `teacher_allowlist` | صف لكل مدرس مسموح (بريد و/أو هاتف، واحد منهما إجباري). فهارس فريدة جزئية على الصيغة المطبّعة نفسها التي تقارن بها البوابة. إدارة (قراءة/إدراج/حذف) للأدمن فقط؛ لا UPDATE — التعديل = حذف + إدراج جديد (أثر تدقيقي أنظف). |
| `can_self_register(p_email, p_phone)` | البوابة: مفتوح → true للجميع؛ مقفول → true فقط عند مطابقة صف سماح (بريد بلا حساسية حالة، أو هاتف مقصوص). منفَّذة لـ `anon` عمداً — تُستدعى **قبل** signUp بلا جلسة. الرد بوليان فقط. |
| `create_teacher_profile_for_self(p_display_name, p_phone)` | **نقطة الإنفاذ الحقيقية**: إنشاء ملف المدرس + إعداداته عبر RPC ‏security definer، تتحقق من البوابة ببريد JWT نفسه قبل أي إدراج وترفع `'registration closed'` عند الرفض. آمنة التكرار (صف قائم يُرجع بلا بوابة). الحساب الجديد عبرها يولد `account_activated = false` — داخل الـ RPC فقط، افتراضي العمود يبقى `true` لمسارات الإنشاء الأخرى (بذرة الديمو، السنتر الإضافي). |
| العميل | `checkSelfRegistrationAllowed()` قبل `signUpWithEmail` في LoginPage (رفض برسالة «التسجيل بالدعوة فقط حالياً…») + `ensureTeacherProfile` تحاول RPC البوابة أولاً وتسقط للمسار القديم عند غياب الدالة فقط. غياب دوال 0057 قبل تطبيق المهاجرة = التسجيل المفتوح الحالي (لا قفل وهمي ولا كسر دخول — درس PGRST204 من الخطوة 1). |

## حدود صريحة (تُقرأ قبل أي ادعاء بالقفل الكامل)

1. **تسجيل GoTrue نفسه لا يُقفل بهذه المهاجرة**: أي بريد يقدر ينشئ
   **حساب Auth** حتى مع القفل. ما يُقفل فعلاً هو تحوّله إلى **ملف
   مدرس شغّال**: البوابة ترفض قبل signUp في الواجهة، وRPC الإنشاء
   يرفض خادمياً بعده، والجلسة بلا ملف مدرس تبقى على شاشة «كمّل
   إعداد حسابك» بلا أي بيانات. إغلاق GoTrue نفسه (تعطيل التسجيل
   من إعدادات Auth) خيار لاحق لا يُتخذ هنا.
2. **مطابقة الهاتف ادّعاء قبل التحقق**: الرقم المكتوب وقت التسجيل
   هو المطابَق؛ المرساة التحققية هي البريد (تأكيد البريد يثبت
   ملكيته). مطابقة هاتف مؤكد (ربط الهاتف بعد التحقق) تحسين لاحق.
3. **التطبيع v1**: البريد يُقارن مقصوصاً بلا حالة؛ الهاتف يُقارن
   مقصوصاً حرفياً (`010…` ≠ `+20 10…` ≠ `010-…`). كتابة الرقم
   في قائمة السماح بنفس الصيغة التي سيدخلها المدرس واجب إجرائي
   حتى يُبنى تطبيع أرقام موحّد.
4. **أوراكل العضوية**: `can_self_register` لـ anon يكشف «هذا البريد
   مسموح أم لا» — مقبول (أوراكل «مسجّل أصلاً» قائم بنفس الدرجة)،
   والرد بوليان فقط بلا بيانات صف.
5. **حساب وقع بين القرارين**: من سجّل حساب Auth (وتأكد بريده) قبل
   قلب القفل لكنه لم يكمل إنشاء ملف المدرس، سيرفضه RPC الإنشاء
   بعد القفل — الحل الإجرائي: الأدمن يضيف بريده/هاتفه لقائمة
   السماح (صف واحد SQL) فيكمل الإنشاء فوراً.

## إجراء البايلوت — قلب القفل وتفعيل مدرس واحد (عند قرار المالك بالإرسال)

كلها SQL مباشر / service role — لا واجهة بعد (اللوحة في الخطوة 7):

```sql
-- 1) قفل التسجيل العام
update public.platform_settings set value = 'false'::jsonb
where key = 'registration_open';

-- 2) إضافة مدرس البايلوت لقائمة السماح (بنفس البريد والهاتف اللذين سيسجل بهما)
insert into public.teacher_allowlist (email, phone, note)
values ('pilot@example.com', '01001234567', 'مدرس البايلوت الأول — 3A-892');

-- 3) بعد أن يسجّل وينشأ ملفه (غير مفعّل): تفعيله وحده + توثيق الفعل
update public.teachers set account_activated = true
where id = '<uid مدرس البايلوت>';

insert into public.platform_audit_log (admin_user_id, action, target_teacher_id, details)
values ('<uid الأدمن>', 'account_activated', '<uid مدرس البايلوت>',
        '{"reason": "pilot teacher — first activation"}'::jsonb);

-- 4) التحقق: أي بريد آخر يرفضه can_self_register، وأي حساب غير مفعّل
--    يبقى بلا وصول تشغيلي؛ والرجوع (فتح التسجيل) = الخطوة 1 بقيمة true.
```
