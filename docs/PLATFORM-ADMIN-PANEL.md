# لوحة أدمن المنصة — المهمة 17 (الخطوة 7 من خطة الأدمن)

**المهاجرة:** `0061_platform_panel.sql` (كود فقط — التطبيق الحي عند تجميد فيز 2 + بوابة QA).
**البند:** 3A-892 — «تقدير: 3 ساعة».

## ما الذي بُني

| المكوّن | الوصف |
|---|---|
| `platform_workspaces()` | قائمة مساحات العمل للأدمن: صف تجميعي لكل مدرس (الاسم + بريد المالك + تاريخ الإنشاء + علم التفعيل + باقة الاشتراك وحالته ونهاية تجربته + عدّ الطلاب + آخر نشاط من `activity_log`). حارس أدمن يرفع `not authorized` لغير الأدمن. |
| `platform_indicators()` | مؤشرات المنصة: إجمالي المدرسين/المفعّلين، الجدد في 7 و30 يوماً، إجمالي الطلاب، والاشتراكات موزعة على الباقات الأربع بمفاتيح ثابتة. |
| `platform_set_account_activated(teacher, activated, reason)` | مفتاح تفعيل/إيقاف الحساب (آلية البايلوت) + سطر `account_activated`/`account_deactivated` في `platform_audit_log` — في نفس المعاملة. الإيقاف لا يمسّ أي بيانات. |
| `platform_set_subscription_plan(teacher, plan_slug, trial_ends_at)` | تعيين باقة من اللوحة (لم يوجد RPC لتغيير الباقة قبل 0061) + تحقق من وجود الباقة + سطر `subscription_plan_changed` في التدقيق. الحالة القائمة تُحفظ عند التحديث. |
| العميل | صفحة `/admin` الكاملة: نظرة عامة (0055) + مؤشرات (0061) + مساحات عمل بإدارة مساحة مختارة (تفعيل/باقة/استحقاقات/تجاوزات) + قائمة سماح (0057) + قسم واتساب نائم. طبقة البيانات `panel.ts` بخطافاتها في `hooks.ts`، والمكوّنات `PanelSection` / `WorkspaceManager` / `labels`. |

## مصادر بيانات كل قسم

| القسم | المصدر | عند غياب المصدر |
|---|---|---|
| المنصة في أرقام | `platform_overview()` (0055) | خطأ مصمم + إعادة محاولة (سلوك الخطوة 1 كما هو) |
| مؤشرات المنصة | `platform_indicators()` (0061) | حالة «قريباً» |
| مساحات العمل | `platform_workspaces()` (0061) | حالة «قريباً» |
| إدارة مساحة: التفعيل | `platform_set_account_activated()` (0061) | رسالة فعل مصممة (`actionError`) |
| إدارة مساحة: الباقة | `platform_set_subscription_plan()` (0061) | رسالة فعل مصممة |
| إدارة مساحة: الاستحقاقات | `effective_entitlements()` (0059) | تلميح «قريباً» داخل البطاقة |
| إدارة مساحة: التجاوزات | قراءة `account_overrides` بسياسة الأدمن + `set_account_override` / `revoke_account_override` (0059) | تلميح «قريباً» داخل البطاقة |
| قائمة السماح والتسجيل | `teacher_allowlist` بسياسات الأدمن + `platform_settings` للقراءة (0057) | حالة «قريباً» |
| إعدادات واتساب المنصة | **لا مصدر بعد** — انظر قاعدة النوم أدناه | حالة «قريباً» دائماً في هذه الخطوة |

كل قراءة لوحة ترجع `null` من طبقة البيانات عند غياب دالتها/جدولها (خطأ «الدالة غير موجودة» فقط)، وقرار `panelSectionState` النقي يعرض «قريباً» — وتسبق «قريباً» الخطأَ عمداً: غياب المهاجرة قبل بوابة التجميد حالة متوقعة لا عطل. أي خطأ آخر يعرض حالة خطأ مصممة بزر إعادة محاولة. **لا خطأ خام في أي قسم** (قاعدة مالك 2026-11-26).

## قاعدة الإيراد المتوقع = null

`platform_indicators()` يرجع `expected_revenue` كـ **JSON null دائماً**، ومحلّل العميل يفرض `null` مهما رجع من الخادم، والواجهة تعرض «—» مع ملحوظة «الأسعار لم تُعتمد بعد». السبب: لا أسعار معتمدة (قرار مالك م1 لم يُتخذ، وجدول `plans` بلا عمود سعر أصلاً في 0058). أي رقم إيراد قبل اعتماد الأسعار اختراع ممنوع؛ حين تُعتمد تُحسب القيمة في مهاجرة لاحقة بقرار موثّق.

## قاعدة نوم قسم واتساب

لا رقم واتساب لمنصة مستر مسجّلاً بعد (التسجيل الأول عند Meta — قرار مالك ق4)، ولا عدّادات استهلاك رسائل في أي جدول (العدّادات مع الخطوة 5/T24؛ جدول `teacher_whatsapp_config` في 0026 يخص أصول Meta الخاصة بكل مدرس لا قناة المنصة). لذلك يعرض القسم حالة «قريباً — لا يوجد رقم واتساب للمنصة بعد» المصممة بقرار `whatsappSectionState` النقي، مع شرح ما سيُدار من هنا لاحقاً (الرقم النشط وتبديله، تفعيل القناة لكل سنتر، سقوف الصرف والحصص، استهلاك الرسائل لكل سنتر). **لا أرقام استهلاك مخترعة ولا قراءة لأصول المدرسين الخاصة في لوحة المنصة.**

## ما أُعيد استخدامه بلا تكرار

- التجاوزات: RPCs وسياسات 0059 كما هي (الكتابة عبر `set/revoke_account_override` فقط، والإلغاء إنهاء لا حذف).
- قائمة السماح: سياسات الأدمن على `teacher_allowlist` (0057) — لا سياسة UPDATE (التعديل حذف + إدراج).
- حالة قفل التسجيل: قراءة `platform_settings` بسياسة الأدمن (0057) **للعرض فقط** — قلب `registration_open` يبقى فعل service role / SQL حتى خطوة لاحقة؛ لا RPC قلب في 0061 عمداً.
- مفاتيح التأكيد (0060): مفاتيح الخصائص `verification_required` وقنواتها تظهر في نموذج التجاوز وقائمة الخصائص الفعّالة بأسمائها — بلا أي مفاتيح جديدة هنا.

## التحقق الدلالي (PostgreSQL 16 مؤقت — أُزيل بعد التمرين)

طُبّقت 0055 ← 0057 ← 0058 ← 0059 ← 0060 ← 0061 على مخطط stub (جداول `teachers`/`students`/`activity_log`/`teacher_settings` + `auth` أدنى) وتمرّنت الدوال: المجهول والمدرس مرفوضان من الدوال الثلاث، صفوف مساحات العمل صحيحة (عدّ الطلاب/الباقة/آخر نشاط)، عدّادات المؤشرات صحيحة و`expected_revenue`‏ JSON null، قلب التفعيل ذهاباً وإياباً مع صفّي تدقيق، تعيين باقة pro مع سطر تدقيق ورفض باقة مجهولة بـ`plan not found`، تجاوز 0059 يظهر في الاستحقاقات الفعّالة، وقراءة RLS المباشرة: الأدمن يرى قائمة السماح والإعدادات والمدرس يرى صفر صف. (0056 لم تُطبَّق في الـstub: جداول البوابة لا تمسّ سطح اللوحة.)

## قائمة فحص بوابة التجميد (قبل النشر)

1. طبّق المهاجرات بالترتيب حتى 0061 (0061 تعتمد `is_platform_admin()` من 0055 وجداول 0057–0059 وقيدي 0060).
2. ازرع أول أدمن (إجراء وثيقة الأساس — service role فقط) وفعّل TOTP إلزامياً لحسابات الأدمن في إعدادات Supabase Auth.
3. شغّل قسم authz الحي لـ 0061 في `scripts/authz_tests.py` (يتخطى نفسه حتى التطبيق): رفض المدرس/المجهول من الدوال الثلاث، قراءة الأدمن للقوائم والمؤشرات، قلب التفعيل يكتب سطر تدقيق، والإيراد null.
4. افتح `/admin` بحساب أدمن: كل الأقسام حية؛ وبحساب مدرس: شاشة الرفض. وتحقق أن قسم واتساب يعرض «قريباً» (لا رقم منصة بعد — الحالة الصحيحة حتى قرار ق4).
5. لا تفعيل طيار ولا قلب لقفل التسجيل قبل قرار المالك بالإرسال (اكتمال فيز 2).
