# قوالب الأدوار الجاهزة — المهمة 18 (الشق المتبقي من الخطوة 4)

**المهاجرة:** `0063_role_templates.sql` (كود فقط — التطبيق الحي عند تجميد فيز 2 + بوابة QA).
**البند:** 3A-893 — «تقدير: 3 ساعة» (الشق المتبقي: القوالب ككيان مستقل؛ التجاوزات الفردية سلّمتها 0059).

## ما الذي بُني

| المكوّن | الوصف |
|---|---|
| `role_templates` | قالب جاهز: `slug` فريد + اسم + وصف + `entitlements` (jsonb بشكل `{features:{}, limits:{}, settings:{}}`) + علم `is_active` + مين عمله. المعطّل لا يُطبَّق؛ ولا حذف أبداً (التعطيل هو الإلغاء، والتاريخ محفوظ). |
| `create_role_template(...)` / `update_role_template(...)` | مسار الكتابة الوحيد للقوالب: حارس أدمن + تحقق خادمي من شكل الحمولة (دالة داخلية `validate_role_template_entitlements` — تنفيذها المباشر مسحوب بنمط 0023) + سطر تدقيق (`role_template_created` / `role_template_updated`) في نفس المعاملة. التعديل استبدال كامل للاسم/الوصف/الحمولة/التفعيل. |
| `apply_role_template(template, teacher, reason, expires_at)` | تطبيق القالب = تجاوز فردي واحد لكل إدخال فيه، عبر `set_account_override` نفسه (لا تكرار لمنطق الإنهاء/الإدراج/التدقيق) + سطر `role_template_applied` يربط القالب بالتجاوزات المكتوبة. يرجع معرّفات التجاوزات المكتوبة. |
| النوع `'setting'` | نوع تجاوز ثالث (0063): `confirmation_channel` بقيمة واحدة من `mobile` | `whatsapp` | `email` — توسّع قيود 0059/0060 (v3) و`set_account_override` و`effective_entitlements()` (خريطة `settings` في المخرجات). |
| العميل | `templates.ts` (قراءة الجدول المباشرة + RPCs الثلاثة + `buildTemplateEntitlements` الخالصة) + خطافات `useRoleTemplates` / `useCreateRoleTemplate` / `useUpdateRoleTemplate` / `useApplyRoleTemplate` + قسم «قوالب الأدوار الجاهزة» في `/admin` (قائمة + إنشاء/تعديل + تفعيل/تعطيل) + «تطبيق قالب جاهز» داخل إدارة كل مساحة عمل. |

## نموذج القالب

- **الخصائص** (`features`): مفاتيح 0059/0060 كلها + `confirmation_required` (تصحيح المالك 17:19) — القيمة بوليان. بلا أي تجاوز يبقى التأكيد الإلزامي مقفولاً.
- **الحدود** (`limits`): المفاتيح الخمسة — القيمة عدد صحيح ≥ 0 أو `null` = بلا حد. التجاوز **يستبدل** قيمة الباقة.
- **الإعدادات** (`settings`): `confirmation_channel` وحده — القيمة نص واحد من الثلاث. قناة بلا إلزام = القناة تُشتق وحدها و`required` يبقى false.
- **القالب نقطة بداية لا قفل**: تطبيق القالب فوق تجاوز سابق لنفس المفتاح ينهيه (قاعدة «الأحدث يفوز»)، والتجاوز اليدوي اللاحق يفوز على القالب المطبَّق.
- **السبب إلزامي** في التطبيق — تطبيق بلا سبب مرفوض خادمياً.

## تمييز موثّق: نظاما تأكيد متوازيان بلا تداخل

- **0060 (3A-905)**: `verification_required` + ثلاثي مفاتيح بوليانية للقنوات — «مجموعة القنوات» المفعّلة = اتحاد المفاتيح.
- **0063 (تصحيح المالك 17:19)**: `confirmation_required` (بوليان) + `confirmation_channel` (قناة واحدة) — الإلزامية وقناتها الواحدة كمفتاحي أدمن.
- العميل يشتق كلاًّ منهما على حدة (`resolveVerificationSettings` / `resolveConfirmationSettings`)، والخادم يحلّهما معاً في `effective_entitlements()`.

## قاعدة عدم رؤية المدرس (جوهر توجيه مالك ٢)

المدرس **لا يرى القوالب إطلاقاً**: لا سياسة قراءة على `role_templates` للمدرس، ولا RPC كتابة له. ما يراه هو **الأثر فقط**: حدوده/خصائصه/إعداداته الفعّالة في `effective_entitlements()` — بلا اسم قالب ولا سبب ولا مين عملها.
